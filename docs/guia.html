1. Antes de escribir código

La parte más importante no se hace en la computadora. Antes de abrir el editor, respondé tres preguntas.

¿Qué hace tu página, en una sola frase?

Si no te sale en una frase, todavía no sabés qué estás haciendo. La nuestra: «anotar cómo te sentís y ver cómo fue cambiando». Esa frase después sirve para decidir: todo lo que no la ayude, sobra.

¿Qué datos necesitás guardar?

Escribí en papel qué información guarda cada cosa. En nuestro caso, cada registro tiene fecha, emoción, intensidad y una observación.

Lo que nos pasó Guardábamos la intensidad del 0 al 10 y parecía suficiente. Cuando quisimos pintar el calendario nos dimos cuenta de que la intensidad sola no dice si el día estuvo bien o mal: un 9 de felicidad y un 9 de enojo son opuestos y los dos son «9». Faltaba un dato: si la emoción es agradable o difícil. Pensar los datos al principio te ahorra rehacer cosas después.

¿Cómo se ve, más o menos?

Dibujalo en papel. No tiene que quedar lindo: alcanza con saber qué secciones hay y en qué orden. Vas a escribir mucho mejor el HTML si ya sabés qué partes existen.

2. Los tres archivos

Un proyecto web chico necesita tres archivos y nada más:

mi-proyecto/
  index.html      qué hay en la página
  css/style.css   cómo se ve
  js/script.js    qué hace cuando la usás
  img/            las imágenes

Se pueden mezclar los tres en un solo archivo, y al principio parece más cómodo. No lo hagas. Separados, cuando algo se ve mal sabés que está en el CSS, y cuando algo no responde sabés que está en el JavaScript. Con todo junto, cada búsqueda es en un archivo gigante.

Se enganchan desde el HTML:

<link rel="stylesheet" href="css/style.css">   <!-- en el <head> -->
<script src="js/script.js"></script>          <!-- al final del <body> -->

El <script> va al final, justo antes de cerrar </body>. Si lo ponés arriba, el JavaScript se ejecuta antes de que exista el HTML y no encuentra nada.

3. HTML: la estructura

El HTML dice qué hay, no cómo se ve. Esa distinción es la que más cuesta al principio y la que más rinde después.

Usá la etiqueta que corresponde

Casi todo se puede hacer con <div>. Casi nada conviene hacerlo así.

Evitá 
<div onclick="guardar()">
  Guardar
</div>

No se puede usar con el teclado, un lector de pantalla no sabe que es un botón, y no responde a Enter ni a la barra espaciadora.

Mejor 
<button type="button">
  Guardar
</button>

Gratis: foco con Tab, se activa con Enter, y quien no ve la pantalla escucha «botón, Guardar».

Las que vas a usar siempre:

  • <header>, <nav>, <main>, <footer> para las zonas grandes.
  • <section> para cada bloque con su propio título.
  • <button> cuando algo hace una acción; <a> cuando lleva a otro lado. Si te confundís, preguntate: ¿esto cambia de página? Es un enlace. ¿Hace algo acá mismo? Es un botón.
  • <ul> con <li> adentro para listas. Solo <li>: meter un <div> suelto dentro de una lista es HTML inválido.

Los formularios necesitan etiquetas asociadas

<label for="emocion">Emoción</label>
<select id="emocion">...</select>

El for tiene que coincidir con el id. Con eso, tocar el texto «Emoción» activa el campo —más fácil en un celular— y un lector de pantalla dice qué es ese campo. Sin eso, dice «combo box» y nada más.

Una prueba rápida Navegá tu página usando solo la tecla Tab, sin tocar el mouse. ¿Podés llegar a todo? ¿Se ve dónde estás parado? Si la respuesta es no, hay algo para arreglar.

4. CSS: la apariencia

Variables: escribí el color una sola vez

Arriba de todo declarás tus colores y medidas, y después los usás por nombre. Cuando quieras cambiar el celeste, lo cambiás en un lugar. 

:root {
  --celeste: #7ed8ff;
  --texto: #0c1723;
  --borde: #afdffb;
  --ancho-caja: min(92%, 900px);
}

.tarjeta {
  border: 1px solid var(--borde);
  color: var(--texto);
}

Que no crezca sin límite

Si a una caja le ponés width: 92%, en un monitor grande se estira hasta ser ilegible: líneas larguísimas que cansan al leer. Si le ponés un ancho fijo en píxeles, en el celular no entra. 

width: min(92%, 900px);

Se lee: «el 92% del ancho, pero nunca más de 900 píxeles». En pantalla chica manda el porcentaje, en pantalla grande manda el tope.

Cuidado con las reglas que no hacen nada Poner width: 50% y max-width: 97% juntos no sirve de nada: el 50% nunca va a superar el 97%, así que el máximo nunca se aplica. Es fácil escribir CSS que parece hacer algo y no hace nada. Si dudás, cambiá el valor a algo exagerado y mirá si cambia algo en pantalla.

El celular primero

Escribí los estilos pensando en pantalla chica, y después agregá lo que cambia en pantalla grande: 

.tarjeta { width: var(--ancho-caja); }   /* vale para todos */

@media (min-width: 900px) {             /* solo en pantalla grande */
  .tarjeta { padding: 24px; }
}

El número donde cortás no es mágico: elegilo mirando dónde tu diseño empieza a verse apretado. En nuestro proyecto tuvimos que subirlo cuando agregamos un ítem al menú y dejó de entrar.

Que se vea dónde está el foco

button:focus-visible {
  outline: 3px solid var(--celeste);
  outline-offset: 2px;
}

Muchos tutoriales enseñan a sacar ese borde porque «queda feo». No lo saques: es lo único que le indica a alguien que navega con teclado dónde está parado. Si no te gusta cómo se ve, hacé uno lindo.

Respetá a quien pide menos movimiento

Los sistemas operativos tienen una opción para reducir animaciones, porque a algunas personas les provocan mareos. El CSS puede escucharla: 

@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    transition-duration: 0.01ms !important;
    animation-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}

5. JavaScript: el comportamiento

Funciones chicas con nombre claro

Una función debería hacer una cosa y llamarse como esa cosa. guardarRegistros(), mostrarAviso(), actualizarInterfaz(). Si para nombrar una función necesitás una «y» —leerYDibujarYGuardar()— probablemente sean tres funciones.

textContent, no innerHTML

Riesgoso 
p.innerHTML = observacion;

Si la persona escribió algo que parece HTML, el navegador lo interpreta como código. Es la puerta de entrada de un ataque clásico.

Seguro 
p.textContent = observacion;

Lo que escribió se muestra tal cual, como texto. Usá innerHTML solo con texto que escribiste vos.

Leé a la defensiva

Todo lo que viene de afuera puede venir mal: lo que escribió una persona, un archivo que importaron, lo que quedó guardado en el navegador. 

function leerRegistros() {
  try {
    const crudo = localStorage.getItem("registros");
    const datos = JSON.parse(crudo);
    return Array.isArray(datos) ? datos : [];
  } catch (error) {
    return [];   // si está roto, devolvemos una lista vacía
  }
}
Por qué importa En nuestro proyecto, un solo dato dañado hacía que la página entera dejara de cargar: no se veía el formulario, ni el historial, ni nada. Con ese try, un dato roto se descarta solo y el resto sigue funcionando.

Cuidado con los tipos

En JavaScript, 5 + 5 da 10 pero "5" + "5" da "55". Si un número quedó guardado como texto, los promedios dan cualquier cosa. Convertí siempre que leas: 

const intensidad = Number(registro.intensidad);

6. Decisiones de UI/UX

Esto no es «que quede lindo». Son decisiones que cambian si alguien puede usar tu página o se frustra y se va.

Los botones se tocan con un dedo

En celular, algo de 30 píxeles es casi imposible de tocar sin errarle. Apuntá a 44 píxeles de alto y ancho como mínimo. En nuestro calendario los días quedaron de 32 px y hubo que rehacer el ancho de esa tarjeta.

En lo irreversible, el camino fácil es el seguro

Cuando abrís un cartel de «¿borrar todo?», el foco tiene que arrancar en Cancelar, nunca en el botón que borra. Si alguien aprieta Enter de reflejo, que cancele.

Decí qué se pierde, no «¿estás seguro?»

Vago

«¿Estás seguro?»

No le da a nadie con qué decidir.

Concreto

«Se van a borrar 12 registros. Esto no se puede deshacer.»

Y si podés, ofrecé la salida: «descargalos antes».

No interrumpas a quien está escribiendo

Si tu página se actualiza sola, no la recargues mientras alguien escribe: le borrás lo que estaba cargando. Mostrale un aviso con un botón y que decida cuándo.

No dependas solo del color

Nuestro calendario pinta los días de rojo a verde, pero además pone una carita distinta en cada nivel. Quien no distingue bien los colores lee la cara. Cuando uses color para comunicar algo, sumale una segunda señal: una forma, un ícono, un texto.

Si el JavaScript falla, que igual se vea

Es tentador poner opacity: 0 en el CSS y que el JavaScript lo muestre al aparecer. Si el JavaScript falla, el contenido queda invisible para siempre. La clase que oculta tiene que ponerla el JavaScript: así, si no corre, no oculta nada.

Mensajes que dicen algo

«Error» no ayuda. «El archivo no tiene el formato esperado» sí. Y cuando algo sale bien, decilo también: «Se actualizaron 12 registros».

7. Privacidad

Si tu página guarda algo de quien la usa, tenés que contarlo. Y acá va la regla más importante de toda esta guía:

El aviso se escribe leyendo tu código No copies uno de internet. Nos pidieron «un aviso de cookies» y al revisar el código descubrimos que la página no usa ni una sola cookie. Poner el cartelito típico habría sido decir algo falso sobre nuestro propio proyecto.

Un aviso honesto responde cuatro preguntas:

  1. Qué se guarda. Con nombres concretos.
  2. Dónde. ¿En el dispositivo? ¿En un servidor? ¿Se envía a alguien?
  3. Quién puede verlo. Ojo con las computadoras compartidas.
  4. Cómo se borra. Y dale un botón para hacerlo.
Mantenelo al día Cuando agregamos la visita guiada, hizo falta guardar un dato más. Eso obligó a actualizar el aviso, que decía «se guardan dos cosas» y las listaba. Si hubiéramos agregado el dato sin tocar el aviso, el aviso habría pasado a ser mentira sin que nadie se diera cuenta.

8. Git y GitHub

Git guarda la historia de tu proyecto en tu computadora. GitHub es un lugar en internet donde subís esa historia para no perderla y para trabajar con otras personas. Son cosas distintas: Git funciona sin internet.

Arrancar

git init                       # crear el repositorio
git add .                      # marcar todo lo que querés guardar
git commit -m "Primera versión de la página"

El ciclo de todos los días

git status                     # ¿qué cambió?
git add index.html css/style.css
git commit -m "Agregar el formulario de registro"
git push                       # subirlo a GitHub

Qué es un buen mensaje de commit

El mensaje lo vas a leer dentro de seis meses, cuando no te acuerdes de nada. Escribí qué cambió, y si la decisión no es obvia, por qué.

No sirve

cambios

arreglos

asdasd

Sirve

Agregar el calendario mensual

Corregir el promedio: las intensidades guardadas como texto se sumaban mal

Commits chicos y seguidos

Un commit por cosa terminada, no uno gigante al final del día. Si algo se rompe, podés volver a un punto donde funcionaba sin perder todo lo demás.

Publicar con GitHub Pages

En tu repositorio, entrá a Settings → Pages y elegí la rama desde la que querés publicar. A los minutos tu página está en https://tu-usuario.github.io/tu-repositorio/, gratis y con HTTPS.

Un detalle que rompe proyectos Ahí tu página no vive en la raíz del dominio, sino en una subcarpeta. Si escribís rutas que empiezan con barra —/css/style.css— van a apuntar al lugar equivocado. Usá rutas relativas: css/style.css, ../img/logo.png.

9. Trabajar en equipo con ramas

Qué es una rama

Imaginá que el proyecto es un cuaderno. La rama principal —se llama main— es la versión en limpio: lo que funciona, lo que está publicado. Cuando querés probar algo, en vez de escribir encima del cuaderno en limpio, sacás una fotocopia y trabajás ahí. Si sale bien, pasás los cambios al limpio. Si sale mal, tirás la fotocopia y no pasó nada.

Esa fotocopia es una rama.

Cómo se usa

git checkout -b calendario     # crear una rama y cambiarse a ella
# ... trabajás, hacés commits ...
git push -u origin calendario  # subirla a GitHub

En GitHub, esa rama aparece como algo separado de main. Ahí abrís un Pull Request: un pedido de «miren esto que hice, ¿lo pasamos al limpio?». Tus compañeros pueden leer los cambios, comentar y pedir correcciones. Cuando está aprobado, se hace merge y los cambios entran a main.

Por qué sirve en equipo

  • Cada uno trabaja en lo suyo sin pisar al otro. Vos en el calendario, tu compañera en las estadísticas.
  • main siempre funciona. Si alguien rompe algo, lo rompe en su rama.
  • Antes de que algo entre, alguien más lo mira. Se aprende mucho leyendo código ajeno.

Los conflictos

Si dos personas cambian las mismas líneas del mismo archivo, Git no sabe cuál vale y avisa que hay un conflicto. No es un error tuyo ni algo grave: te muestra las dos versiones y elegís.

Para que pasen poco:

  • Repártanse las tareas por archivo o por sección.
  • Ramas cortas: una tarea, se mezcla, se borra la rama.
  • Traigan seguido los cambios de los demás con git pull origin main. Cuanto más tiempo pasa una rama separada, más se aleja y más difícil es mezclarla.

Ponerle nombre a las ramas

calendario
arreglo-promedio
estilos-movil

Que el nombre diga qué hay adentro. rama2 y prueba-final-final no le sirven a nadie.

10. Trabajar con una IA

Una IA te puede ayudar mucho, y también te puede hundir si la usás mal. La diferencia está casi toda en cómo le pedís las cosas.

El error más común: pedir todo de una

Así no

«Hacé una página para registrar emociones con calendario, estadísticas y que se pueda descargar.»

Te va a devolver cientos de líneas de golpe. Si algo anda mal, no sabés dónde. Si querés cambiar algo, no entendés qué tocar. Y no aprendiste nada: tenés código que no sabés explicar.

Así sí

«Quiero un formulario con un campo de fecha, un select de emociones y un textarea. Solo el HTML, sin estilos todavía.»

Lo mirás, lo entendés, lo probás. Y recién después pedís lo que sigue.

Desglosá antes de pedir

Agarrá tu idea y partila en pedazos que se puedan probar por separado. Para nuestro proyecto sería más o menos así:

  1. El HTML del formulario.
  2. Que al enviarlo se guarde en el navegador.
  3. Que se muestre la lista de lo guardado.
  4. Los estilos de esa lista.
  5. El buscador.
  6. El calendario.

Cada paso se prueba en el navegador antes de pedir el siguiente. Si el paso 3 quedó raro, lo arreglás ahí, no cuando ya hay seis capas encima.

Dale contexto

Una IA no adivina. Contale qué hay, qué usás y para quién es: 

«Tengo un index.html con un formulario que ya guarda en
localStorage bajo la clave "registros". Quiero agregar una lista
que muestre lo guardado. Es para un taller de secundaria, así que
preferí código simple y sin librerías.»

Pedí que te explique

Agregá «explicame qué hace cada parte». Si no entendés el código que te dio, no lo pegues: preguntá. El objetivo del taller es que aprendas, no que la página exista.

Revisá siempre

La IA se equivoca con mucha seguridad Te va a dar código que parece perfecto y a veces está mal. En este mismo proyecto, la visita guiada iluminaba la sección equivocada, y había una prueba automática que daba «todo bien»... porque comprobaba exactamente lo que el código hacía mal. Se descubrió cuando una persona lo miró en la pantalla.

Probá en el navegador siempre. Que no tire errores no significa que haga lo que querés.

Pedile que no haga de más

Si pediste un botón y te reescribió medio archivo, decíselo: «solo agregá el botón, no cambies lo demás». Cambios chicos son cambios que podés revisar.

Usala para entender, no solo para producir

Estas preguntas valen más que «escribime esto»:

  • «¿Por qué conviene <button> y no <div>?»
  • «¿Qué puede salir mal en este código?»
  • «¿Hay una forma más simple de hacer esto?»
  • «Explicame este error como si recién empezara.»

11. Un orden para arrancar

  1. Escribí en una frase qué hace tu página.
  2. Dibujá en papel las secciones.
  3. Anotá qué datos vas a guardar.
  4. Creá los tres archivos y el repositorio (git init).
  5. Escribí el HTML de todo, sin estilos. Feo pero completo.
  6. Commit. Es tu punto de retorno.
  7. Estilos básicos: colores, tipografía, espacios.
  8. La primera función de JavaScript: la más importante de todas.
  9. Probala en el navegador. Commit.
  10. Subila a GitHub y publicala con Pages, aunque esté a medias.
  11. De ahí en más: una función por vez, probar, commit.
Publicá temprano Tener la página en internet desde el primer día, aunque esté incompleta, te obliga a que ande de verdad y te deja mostrarla. Es muchísimo mejor que tener algo perfecto en tu computadora que nadie vio nunca.

Para cerrar

Si te llevás cinco cosas de todo esto:

  1. Lo que viene de afuera puede venir mal. Leé a la defensiva.
  2. Medí antes de suponer. Nuestro logo pesaba 1,9 MB para mostrarse a 40 píxeles y nadie lo había notado.
  3. Pensá los datos al principio. Faltaba saber si una emoción era agradable o difícil, y no se notó hasta el calendario.
  4. Lo que decís sobre tu programa tiene que ser verdad. El aviso de privacidad se escribe mirando el código.
  5. Una prueba que pasa no significa que el código esté bien. Significa que hace lo que la prueba dice. Si la prueba está escrita mirando el código en vez de lo que tiene que lograr, se equivocan juntas.
